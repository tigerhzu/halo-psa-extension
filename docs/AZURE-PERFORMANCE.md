# Azure 回應速度

## 1.1.5 延遲修正（2026-09-22）

使用者提供的畫面：總耗時 28.3 秒，API 28.0 秒、輸出 41 tokens，並確認已選「關閉 Thinking」。這只能定位到 API 等待／生成／傳輸階段，無法單憑畫面區分排隊、網路與模型生成。程式確認每次只送一個請求，沒有隱藏的重試。

- 關閉 Thinking 時，按原文長度與行數配置 768–4096 的輸出上限；範例三行工單從固定 4096 降為 768。原文與所有 prompt 規則完整保留，長文上限仍為 4096，服務預設推理模式維持原有額度。
- 非推理連線測試只預留 32 tokens，設定頁顯示實際測試耗時。
- Azure 的 120 秒背景截止時間涵蓋 fetch 與讀取回應本文；到期中止，不再讓前端逾時後背景仍無限等待。不自動重試；截斷回應維持拒絕套用。
- 預覽顯示等待回應標頭、讀取完整回應、輸出上限與送出的 Thinking 模式。標頭時間不等於首字延遲，請求模式也不等於服務端已採用。

降低不必要的 max_tokens 預留參考 [Microsoft Azure 延遲說明](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/latency)。是否能改善這個 DeepSeek 部署必須實測，不能把參數優化當成已確認的伺服器根因或速度保證。

驗證範圍：自動化測試涵蓋動態額度、原文與 prompt 不變、單次請求、截斷保護、標頭與本文逾時中止、計時器清理。未取得實際 Edge 的 Azure 連線，因此未執行正式部署前後測速。

驗證結果：完整測試 100 通過、0 失敗、1 略過（缺少歷史 0.9.11 來源）；78 個 manifest 資源、JavaScript 語法與 diff 空白檢查通過。本機瀏覽器確認效能明細、原文、草稿與底部操作按鈕可見。實際安裝目錄已更新為 1.1.5，僅五個預期檔案變更，程式 SHA256 與工作區一致。

## Thinking 設定

在擴充功能 AI 設定中，將 Thinking 模式設為「關閉 Thinking（DeepSeek）」後測試連線，再比較相同文字的處理時間。設定會自動儲存。既有部署預設保持「服務預設」，因為部署名稱不代表實際模型，也不能保證所有 Azure 模型接受 DeepSeek 的參數。

此選項送出 `thinking: { type: "disabled" }`，依據 [DeepSeek 文件](https://api-docs.deepseek.com/guides/thinking_mode/)。Azure 部署是否接受並採用此參數必須實測；成功回應但未回報推理用量不等於已證明關閉推理。不支援時改回「服務預設」。不會自動重試或切換供應商。

## 測速

使用 Node.js 22 或以上版本，在本機程序環境中設定 `AZURE_OPENAI_ENDPOINT`、`AZURE_OPENAI_DEPLOYMENT`、`AZURE_OPENAI_API_KEY`，再執行：

```text
node scripts/benchmark-azure.cjs
```

請勿把金鑰提交到版本控制或貼進對話。工具會對指定 Azure 部署發出六次請求，使用固定的虛構 Wi-Fi 維修文字，交替比較服務預設與關閉 Thinking 各三次。這些請求依 Azure 用量計費。結果只輸出數值與模式，不記錄金鑰或模型回覆。HTTP 失敗或回覆不完整時停止。

70 tokens/s 的判斷使用三次全程平均速度的中位數，包含服務等待及傳輸時間。推理用量未知時以回報的 completion tokens 計算，仍需審慎比較；此數值不是串流生成速度。以 98 個輸出 tokens 為例，要達到全程平均 70 tokens/s，整個 API 請求需在約 1.4 秒內完成。

若關閉 Thinking 後仍無法達標，需要在 Azure 比較其他適合潤稿的部署或服務容量。擴充功能無法保證伺服器吞吐量，串流也不會直接提高模型的生成速度。
